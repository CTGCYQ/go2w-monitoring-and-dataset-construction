# 高斯场景、地图分块与定位方案评估

日期：2026-10-23。状态：方案评估，未训练高斯地图，未改变生产定位、渲染器或运动门禁。

## 目标与分层

使用雷达、RGB-D 和经过校验的位姿构建真实场景；3D Gaussian Splatting（3DGS）负责照片级外观，几何地图负责测距/障碍/可通行性，定位地图负责位姿跟踪和重定位。三者共享明确的 map_id、版本、单位、坐标系和标定记录。

建议先完成“采集 → 离线重建 → 分块发布 → 浏览器浏览”，再评估在线增量高斯建图。实时位姿与动态障碍继续独立更新，静态高斯底图不会因相机当前画面变化而被错误解释为实时世界。

## 当前项目的前置工作

- 深度接收器目前强调 RAM-only Z16；独立 JPEG 缓存与低频录制快照不能直接视为同一时刻的 RGB-D 训练帧。需记录同一 frameset 的 RGB、原始深度、帧号、时间域、内参和曝光等元信息。
- 扩展坞 NTP 未完成同步的既有问题仍需解决；同时测量相机、雷达与 IMU 的时间域关系。接收时间可用于判断新鲜度，不能直接冒充曝光/测量时刻。
- 补全并验收相机—雷达—机身外参、尺度、方向与姿态链；原装安装位置不等于当前软件已有可靠标定值。
- Point-LIO 当前提供局部里程计；现有有界体素显示缓存不等于可长期复用、闭环优化和开机重定位的全局地图系统。
- 训练 GPU 尚未核实：本轮在 80 服务器执行 nvidia-smi 返回 command not found，不能由此断言没有 GPU，也不能承诺当前服务器的训练速度或显存容量。

## 建模链路

1. 采集同步 RGB-D、雷达关键帧与 IMU/LIO 轨迹，保存源时间、时钟映射和标定版本；清晰度/覆盖/曝光筛选关键帧，静止重复图像不无限入库。
2. 雷达约束米制结构与初始轨迹，加入闭环与全局优化；优化后导出一致的相机位姿及子图变换。
3. 在训练工作机上使用 gsplat 试制一个房间/走廊的小样；使用 RGB 外观损失及适配的深度/几何约束，不把简单点云转成大点精灵冒充真实 3DGS 训练。
4. 去除漂浮、冗余高斯，过滤人员、机器狗自身等动态遮挡。未观测区域标明覆盖不足，禁止用视觉“补全”结果当作测量事实。
5. 以子图为单位生成发布版本及 LoD，验证跨子图接缝。闭环改变子图位姿时重新优化/发布受影响块，而不是仅挪动机器人图标。

## 存储管理

地图按场地/楼层/区域及八叉树或自适应空间子图组织。manifest 记录包围盒、局部原点、到场地坐标变换、覆盖范围、LoD 误差、资源字节数、hash、标定版本与来源采集会话。

分三类保留：原始训练关键帧（可追溯与再训练）、训练检查点（研发恢复）、只读发布资产（前端加载）。不同保留策略和配额，不能只删除旧 PLY 就宣称解决存储增长；发布地图校验通过、备份和保留策略满足后才清理允许清理的数据。

SPZ 用于紧凑归档与交换；官方报告相对常见 PLY 约 10 倍压缩，但实际比率需用本项目数据测量。浏览器流式发布可预生成 Spark RAD/LoD 页，不能假定任意 SPZ 文件本身具备空间随机访问能力。归档格式版本与前端解码器需成对固定并做兼容测试。

压缩磁盘字节数不等于解码内存、GPU 纹理、LoD 树、排序双缓冲和工作线程占用。服务端分别统计 raw/checkpoint/published/cache 容量；前端分别统计加载字节、常驻页、可见高斯及估算 GPU 分配。

## 展示、加载与渲染范围

| 范围 | 管理对象 | 方案 |
| --- | --- | --- |
| 地图保存范围 | 场地所有已发布数据 | 空间索引、版本清单、配额与按块增量更新 |
| 浏览加载范围 | 当前视角附近且已解码的资源 | 视锥与区域筛选、邻域预取、LRU 淘汰、请求取消 |
| 实际渲染范围 | 当前帧参与绘制的高斯 | 屏幕投影误差驱动 LoD、可见高斯预算、自适应分辨率 |
| 定位搜索范围 | 几何/特征地图与候选子图 | 位姿先验与全局检索，不依赖浏览器相机的可见范围 |

引入 Spark 前需核对现有全局脚本式 Three.js 的版本兼容性与渲染生命周期，必要时使用独立构建的 3D 模块，避免影响已有点云视图。

首先加载低细节概览，再加载当前位置附近精细页；远景保持低细节，未加载块按需要获取，不下载全场再隐藏。大半径高斯会造成像素过绘，单纯限制点数不足以限制帧耗时。

应用共享的资源预算与并发下载上限，切换场地/版本取消旧下载、排序任务并释放 GPU 资源；切出 3D 页面暂停绘制。固定世界地图与实时障碍/机器人轨迹分开更新，避免每次遥测刷新重新下载高斯底图。

机器人跟随模式与自由漫游模式分开；自由视角移动只改变浏览加载区域，不能改变机器人的物理定位或后端定位子图。用户可以控制显示半径/楼层/裁剪高度，最终细节仍受帧时间与内存预算约束。

初始性能目标（尚未实测）：桌面浏览 30 FPS、相机移动后逐级加载而非卡死、可配置缓存与高斯预算、跨区域重复进出后资源不持续增长。先用实际浏览终端测量后确定默认预算，不承诺固定百万高斯在所有终端均达标。

## 定位与多机器人

统一物理链：场地 map → 每台机器人自己的 odom → base_link → 相机/雷达。相机光学坐标、ROS 机身坐标与 Three.js/SPZ 坐标需要明确转换；不能再次靠显示轴标签或经验角度掩盖方向问题。局部块原点可避免大坐标量化损失，但定位仍使用统一米制场地坐标。

- 连续跟踪：沿用已验收的雷达/IMU 里程计，并监测质量、跳变和协方差/匹配置信度。
- 全局一致性：闭环检测与子图优化，纠正长期漂移，输出 map→odom。
- 冷启动与失跟恢复：场地/子图检索、几何匹配和置信度核验；有视觉定位时作为额外候选/约束。只靠近邻 ICP 或上一帧位姿不能保证任意位置重定位。
- 失败处理：显示“未定位/重定位中/低可信”，不把零点或最后一帧当作当前可靠位置；依赖定位的作业不继续执行。
- 多机器人：同一场地共享同一地图发布版本，每台机器人保留自己的里程计、轨迹和地图对齐变换。跨机器人子图只有通过重叠区域匹配及几何检验后才合并，不自动假定两个局部原点相同。

SplaTAM 等研究已探索 RGB-D 高斯跟踪建图，可做后续实验对照；本项目第一阶段以可验证的几何定位为主，并行评估高斯视觉重定位，不直接替换现有定位主链。

## 与平台整合及实施顺序

新增场地地图资产、采集会话、构建作业和发布版本的独立实体。机器人是采集者和地图使用者，场地地图不是每个机器人的重复副本。

作业工作台可逐步增加“场景采集 → 数据检查 → 几何优化 → 高斯训练 → 压缩/LoD → 质量验收 → 发布”流程，每一步读取实际任务与产物状态；训练可在其他 GPU 工作机执行，监控服务器继续提供状态与地图服务。现有固定作业模板需扩展执行器后才支持上述流程，不能只新增前端状态标签。

建议待办顺序：

1. 修复校时并审计源时间关系，完成外参、尺度及轨迹闭环验收。
2. 补齐同步 RGB-D/LiDAR/pose 训练数据包及质量检查；确认可用 GPU。
3. 一个房间/走廊的离线 3DGS 小样，验证外观、米制几何对齐和未见视角。
4. 地图 manifest、分块压缩、服务器缓存与 Spark LoD 分页浏览，测实际终端资源。
5. 地图持久化定位/冷启动重定位与多机器人坐标统一。
6. 扩展建图作业流水线、增量更新；最后评估在线高斯 SLAM。

验收分开记录：外观留出视角质量、尺度/控制点误差、闭环与重定位成功率及恢复时间、文件压缩率、首屏加载、帧时间分位数、CPU/GPU/缓存占用。好看的图、较小的文件和定位准确分别验收，不能互相代替。
